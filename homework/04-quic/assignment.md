Вы — разработчик, которому передали три проблемы. Для каждой
ситуации подготовьте короткий инженерный разбор:

1. **Причина:** что происходит и почему? Отделите факты от предположений.
2. **Исправление:** что конкретно изменить в клиенте, сервере или API и почему?
3. **Проверка:** какой тест провести и по каким наблюдениям оценить результат?

Вопросы под каждой ситуацией уточняют, что должно попасть в разбор. Не нужно
повторять условие или давать определения всех терминов. Если данных недостаточно,
назовите недостающее наблюдение; обоснуйте выбранную гипотезу.

**Сдача:** один `REPORT.md` с тремя разделами в своём GitLab с доступом
преподавателям, как в ДЗ 1. Можно писать абзацами, списками или псевдокодом.
Ориентир — 5–10 предложений на ситуацию, но обязательного объёма нет.

Это модельные ситуации: писать код, запускать стенд и снимать tcpdump не нужно.
Опишите проверки словами. Важны объяснение причин и связь

## 1. Перешли на HTTP/3, но страница всё равно тормозит

Вы разрабатываете страницу товара. Браузер параллельно запрашивает большую
фотографию и небольшой JSON с информацией о наличии товара на складе. При HTTP/2 оба ответа идут через
одно TCP-соединение. На сети с потерями сведения о наличии товара на складе иногда появляются
с заметной задержкой, хотя API отвечает быстро.

Команда включает HTTP/3 и проверяет, что браузер действительно использует его.
В повторных тестах на той же сети сведения о наличии товара на складе обычно появляются раньше,
а фотография по-прежнему иногда загружается медленно.

Затем выясняется, что в мобильной версии страницы запрос наличия товара запускается
только после полной загрузки фотографии. В этой версии улучшения почти нет.

**Что написать в разборе:**

- Какую задержку мог уменьшить HTTP/3? Почему это не помогает, когда фронтенд
  сам ждёт фотографию? Объясните, что изменить в клиенте. Не считайте наблюдения
  доказательством единственной причины тормозов.
- Коллега предлагает передавать фотографию через QUIC DATAGRAM: «Не будем
  повторять потерянные пакеты — картинка придёт быстрее». Что не так с этим
  предложением? Разработка собственного протокола в ответе не требуется.
- Как проверить вашу гипотезу и исправление? Опишите сравнение и назовите
  наблюдения, по которым отличите задержку в сети от ожидания во фронтенде.

## 2. Сеть сменилась — загрузка начинается заново

Вы разрабатываете клиент облачного хранилища. Пользователь отправляет большой
файл с ноутбука. При переходе с WiFi на встроенный LTE-модем прогресс сбрасывается,
и файл начинает загружаться заново.

Клиент уже использует HTTP/3. Библиотека и сервер поддерживают миграцию QUIC,
но в клиенте есть такой обработчик:

```text
При изменении сети:
    отменить текущие запросы
    закрыть HTTP-клиент
    создать новый HTTP-клиент
    начать загрузку заново
```

Сейчас файл отправляется одним HTTP-запросом. API не умеет узнавать, какая часть
файла уже сохранена, и продолжать незавершённую загрузку.

**Что написать в разборе:**

- Почему QUIC не спасает загрузку при таком обработчике? Что изменить, чтобы
  дать соединению возможность пережить смену сети?
- Что понадобится на уровне клиента и API, если связи нет несколько минут
  или приложение закрыли и открыли снова? Опишите принцип продолжения загрузки,
  без проектирования всех эндпоинтов и форматов.
- Предложите две проверки: короткая смена сети и восстановление после закрытия
  приложения. Как убедиться, что файл не отправляется целиком повторно и в итоге
  сохранён корректно? Одного непрерывного индикатора прогресса недостаточно.

## 3. Перевод денег: ответ не пришёл

Алиса хочет один раз перевести Бобу 1000 рублей. До операции у Алисы 5000 рублей,
у Боба 2000. Комиссий и других операций нет.

```text
Клиент → сервер HTTP API → база данных

POST /transfers
{"recipient_id":"bob","amount_kopecks":100000,"currency":"RUB"}
```

Отправитель определяется по аутентификации. API атомарно сохраняет списание,
зачисление и запись перевода, затем отвечает `201`. Каждый успешный POST
без ключа идемпотентности выполняет новый перевод.

При разборе инцидента выяснилось:

1. Клиент отправил запрос на перевод 1000 рублей. TCP-стек сервера подтвердил
   получение всех байтов запроса; клиент получил этот TCP ACK.
2. API выполнил перевод 1000 рублей и отправил HTTP-ответ `201`. Затем связь
   оборвалась: клиент не получил HTTP-ответ до истечения времени ожидания.
3. Клиент получил таймаут. После восстановления связи он открыл новое
   соединение и повторил тот же POST с тем же JSON.
4. API ещё раз выполнил перевод 1000 рублей. На этот раз клиент получил ответ `201`.

В момент таймаута клиент не видел журналы сервера.

Для исправления API можно расширить. Предлагаемый контракт:

- Клиент передаёт `Idempotency-Key`. В пределах пользователя сервер атомарно
  сохраняет ключ, перевод и результат. Повтор того же тела с тем же ключом
  возвращает прежний результат без нового списания; другое тело даёт ошибку.
- По ключу можно запросить состояние: `pending`, `done` с результатом или
  `not_found` на момент проверки. Исходный запрос ещё может быть в пути.
- Защита от повторного выполнения действует 24 часа с первого принятия ключа.

**Что написать в разборе:**

- Что клиент знал при таймауте и что стало известно после изучения журналов?
  Почему TCP ACK не подтверждает перевод? Укажите итоговые балансы.
- Опишите порядок действий для следующего перевода: когда создать и сохранить
  ключ, как действовать при таймауте и разных состояниях операции, когда
  прекратить автоматические попытки и что показать пользователю при
  неизвестном результате. Можно ли исправить уже случившийся инцидент,
  добавив ключ только при повторе первоначального запроса?
- Предложите проверку, которая воспроизводит потерю ответа после успешного
  перевода и доказывает отсутствие двойного списания после исправления.
  Устранит ли эту проблему сама по себе замена TCP на QUIC?
