# Домашнее задание. Диагностический HTTP/HTTPS-клиент

Покрывает результаты обучения недели 1 и недели 2.

## 1. Что сдаётся

- CLI-приложение (`netdiag` далее по тексту — имя условное) с единой точкой входа.
- `README` — как собрать и запустить, какие этапы реализованы.
- `REPORT` — короткий отчёт (раздел 6).
- Для этапа D обязателен хотя бы один автоматический тест на встроенном
  примере, не идущий по сети.

## 2. Функциональные ограничения

Не должно быть заменено готовой библиотекой/фреймворком:

- разбор HTTP-ответа (status line, заголовки, framing — Content-Length и chunked) — HTTP-клиент с автоматическим разбором ответа не используется;
- проверка сертификата целиком через готовый вызов проверки по умолчанию на уровне 1 — имя хоста проверяется собственным кодом; на уровне 2 —
  вся проверка (подпись, издатель, срок, имя) собственным кодом;
- разбор multipart по границам — готовый MIME/multipart-парсер не используется;
- общий флаг/режим, отключающий все проверки сертификата разом без указания конкретной причины — не реализуется ни на одном уровне.

Можно использовать готовые примитивы там, где это не является предметом проверки: распаковку gzip, разбор JSON-грамматики, декодирование текста
по известной кодировке, криптографические примитивы (подпись, хэш) на уровне 2.

## 3. Формат вывода

Для одного запроса печатается блок:

```text
STAGE: <DNS|CONNECT|TLS|HTTP|DECODE|PARSE>
RESULT: <ok|error>
CLASS: <код из таблицы ниже>
FACT: <одна строка — что именно наблюдалось>
NEXT: <следующая проверка; пусто, если RESULT=ok и это конечный этап>
```

| CLASS | Значение |
|---|---|
| `dns_error` | имя не резолвится |
| `connect_error` | TCP-соединение отклонено или недостижимо |
| `timeout` | превышено время ожидания (указать, на каком этапе) |
| `tls_error` | TLS handshake не завершился (уровень 1: доверие или срок) |
| `cert_invalid` | handshake завершился, проверка имени хоста не пройдена (уровень 1) |
| `framing_error` | HTTP-обмен начался, но границы тела нарушены |
| `decode_error` | тело получено полностью, но gzip/charset не восстановились |
| `parse_error` | текст восстановлен, но не является валидным JSON |
| `multipart_error` | HTTP-тело получено полностью, но multipart-границы или части некорректны |
| `http_ok` | получен полный HTTP-ответ, представление восстановлено |

Для уровня 2 (раздел 5.4) допустимы дополнительно `chain_untrusted`,
`cert_expired`, `hostname_mismatch` вместо обобщённых `tls_error`/
`cert_invalid`. При использовании управляемого bypass добавляется строка
`BYPASSED: <что и почему обойдено>`.

Для успешного текстового или JSON-ответа после диагностического блока
выведите `BODY: <JSON-строка>`: полный восстановленный текст без усечения,
с экранированными переводами строк. Для JSON это исходный декодированный
текст, а не повторная сериализация объекта. Например, для `/chunked`:
`BODY: "first-second-third\n"`. Готовый JSON-сериализатор для этой строки
разрешён. При ошибке строка `BODY` не обязательна.

В этапе D выведите части по порядку: заголовки каждой части и полное тело
в hex или Base64 (формат укажите в README). Это позволяет проверить
бинарные данные без потерь. Для `multipart_error` используйте `STAGE: PARSE`.

## 4. Тестовый стенд

`tests/` — самодостаточные локальные фикстуры, описание и запуск в
`tests/README.md`:

- `fixture_server.py` — HTTP-сервер для этапов A, B, D;
- `tls_fixture/` — генератор сертификатов и HTTPS-сервер на 4 портах
  (валидный / просроченный / чужое имя / чужой CA) для этапа C.

`dns_error`/`connect_error` проверяются обращением к несуществующему
имени и к заведомо закрытому порту — стенд их отдельно не производит.

## 5. Задачи

### 5.1. Этап A (обязательный минимум). HTTP/1.1

Что реализовать по URL вида `http://host:port/path`:

- резолвинг имени;
- TCP-соединение;
- сборка запроса (request line, `Host`, `Accept` и т.п.);
- разбор ответа (status line, произвольное число заголовков, тело по
  `Content-Length`).

Критерии приёмки:

| Проверка | Ожидаемый результат |
|---|---|
| `/plain` | `STAGE: HTTP`, `RESULT: ok` |
| `/status/503` | `STAGE: HTTP`, `RESULT: ok`, статус — в `FACT` (HTTP-код не считается сетевым сбоем) |
| несуществующее имя | `dns_error` |
| закрытый порт | `connect_error` |
| `/timeout` с заметно меньшим таймаутом | `timeout` |

### 5.2. Этап B (обязательный минимум). Контракт представления

- `/chunked` — разбор chunked framing.
- `/broken-length` — `framing_error`, без необработанного исключения.
- `/repr?case=...` — декодирующая цепочка строго в порядке
  **content-encoding → charset → JSON**:
  - `decode_error` — не восстановился gzip или charset;
  - `parse_error` — текст восстановлен, но JSON синтаксически невалиден;
  - `FACT` называет, какой именно шаг не выполнился.

Подавление ошибок декодирования текста («декодировать как получится»)
не допускается.

### 5.3. Этап C, уровень 1 (для хорошего и отличного уровня). TLS и проверка сертификата

Для минимального зачёта необходимы полностью выполненные A и B и отчёт.
Этап C считается выполненным при выполнении всех пяти критериев рубрики
(25 из 25 баллов). Без этого базовая оценка не выше 74 баллов; бонусы
не повышают уровень оценки и не заменяют обязательные этапы.

Подключение к одному из четырёх портов стенда, доверенный корень —
файл, выданный стендом.

- Проверка цепочки доверия и срока действия — стандартным механизмом
  платформы.
- Проверка имени хоста — собственным кодом после handshake: сравнение
  запрошенного имени с полями сертификата.

Ожидаемый итог на 4 портах (раскладка порт → сертификат перемешивается
заново при каждом запуске стенда):

| Класс | Сколько портов | Причина |
|---|---|---|
| `http_ok` | 1 | валидный сертификат |
| `cert_invalid` | 1 | несовпадение имени хоста |
| `tls_error` | 2 | разный `FACT`: истёк срок / чужой CA |

### 5.4. Этап C, уровень 2 (по желанию). Собственный chain-валидатор и управляемый bypass

Активируется отдельным режимом/флагом клиента. Стенд — цепочка из
одного звена (корень подписывает лист напрямую).

Проверка сертификата целиком реализуется собственным кодом, без
стандартной автоматической проверки:

- подпись и издатель — против доверенного корня;
- срок действия — отдельной проверкой;
- имя хоста — как в уровне 1.

Ожидаемый итог на тех же 4 портах — три различимых класса вместо двух:

| Класс | Причина |
|---|---|
| `http_ok` | валидный сертификат |
| `chain_untrusted` | чужой CA |
| `cert_expired` | истёк срок |
| `hostname_mismatch` | неверное имя |

Управляемый bypass — принять конкретный, названный дефект осознанно:

1. обойти истёкший срок для конкретного соединения, с явным указанием
   в выводе (`BYPASSED: expired ...`);
2. обойти несовпадение имени — аналогично;
3. принять конкретный сертификат по отпечатку (pinning), даже если
   цепочка не подтверждена — с проверкой, что заведомо неверный
   отпечаток ничего не обходит.

Общий флаг, отключающий все проверки сразу, запрещён (раздел 2).

### 5.5. Этап D (бонус). Multipart вручную

- `GET /multipart` — разбор `multipart/mixed` по границе из
  `Content-Type` без готового multipart-парсера: заголовки и тело
  каждой части.
- `GET /multipart-broken-boundary` — не должен приводить к падению,
  только к `multipart_error` с указанием нарушения границы в `FACT`.

## 6. Отчёт `REPORT` (обязательная часть, не бонус)

До одной страницы:

1. Для каждого фактически воспроизведённого класса из таблицы раздела 3 —
   одна строка: как вызвали, что увидели.
2. Один абзац: почему на уровне 1 «чужой CA» и «истёк» — один класс, а
   несовпадение имени проверяется отдельно. С опорой на свои прогоны на
   портах стенда, не на общую теорию.
   Если этап C не реализован, укажите это; баллы за этот пункт не начисляются,
   но отсутствие TLS-прогонов не препятствует минимальному зачёту.
3. Один абзац: чем HTTP 200 с последующим `parse_error` отличается от
   `framing_error` по тому, что уже гарантировано на момент отказа.
4. Если сделан уровень 2: абзац о том, когда осознанный bypass конкретной
   проверки уместнее, чем отключение проверки целиком.

## 8. Как сдавать

Исходный код и все файлы необходимо выложить в гитлаб и открыть доступ преподавателям.

## 9. Что не проверяется

- HTTP/2, HTTP/3;
- собственная реализация TLS record layer;
- построение полного пути сертификации с промежуточными CA, OCSP/CRL —
  стенд намеренно одноуровневый даже на уровне 2;
- разбор полного формата X.509 — только поля, нужные для проверки имени,
  срока и издателя;
- ASN.1/DER или Protobuf кодирование/декодирование вручную;
- производительность, конкурентные запросы, повторные попытки.
