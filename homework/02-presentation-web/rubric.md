# Рубрика проверки

Проверка ручная. Баллы условные — вес в общей оценке курса определяется отдельно.
Здесь фиксируется распределение внутри задания и наблюдаемые критерии
«сделано / не сделано», а не итоговая шкала курса.

## Общее правило проверки

Каждый критерий проверяется запуском клиента (команда — из README сдачи)
против стенда из `tests/` и чтением вывода в формате раздела 3
`assignment.md`. Проверяющий не читает код построчно для проверки
функциональности — код читается только при подозрении на использование
запрещённых инструментов (раздел 2) или при расхождении вывода с `REPORT.md`.

## Этап A — 30 баллов (обязательный минимум)

| Критерий | Баллы | Как проверить |
|---|---|---|
| Резолвинг имени, отдельный `STAGE: DNS` на `dns_error` | 5 | запрос к несуществующему имени |
| TCP-соединение, `connect_error` на закрытом порту | 5 | запрос на заведомо закрытый порт |
| `timeout` на `/timeout` с явным ограничением времени | 5 | таймаут заметно меньше 30 c — клиент укладывается, а не висит |
| Запрос собран без готового HTTP-клиента с автоматическим разбором ответа | 5 | Чтение кода при сомнении; `/plain` отдаёт `RESULT: ok` |
| Разбор status line и заголовков произвольной длины | 5 | `/status/404`, `/status/503` — `STAGE: HTTP`, `RESULT: ok`, `FACT` называет код |
| Content-Length framing реализован самостоятельно | 5 | `/plain` с телом другой длины (варьировать вручную) |

**Провал любого пункта — этап A не считается выполненным**, задание в
целом ниже проходного балла независимо от этапов B–D.

## Этап B — 30 баллов (обязательный минимум)

| Критерий | Баллы | Как проверить |
|---|---|---|
| Chunked-декодирование `/chunked` | 5 | `RESULT: ok`, `BODY` после разбора JSON-строки равен `first-second-third\n`, включая завершающий перевод строки |
| `/broken-length` → `framing_error`, без необработанного исключения | 5 | Аварийный код возврата/traceback — 0 баллов за пункт |
| Порядок декодирования: gzip → charset → JSON, для всех `case=` из `tests/README.md` | 10 | Все case, включая `gzip-json-ok` → `http_ok` с полным текстом в `BODY` и `gzip-json-bad` → `parse_error`; сверить содержимое успешных ответов, а не только класс |
| `decode_error` отделён от `parse_error` (не всё подряд «ошибка») | 5 | `case=bad-gzip` → `decode_error`; `case=json-bad` → `parse_error` |
| Ошибки декодирования текста не подавляются молча | 5 | Чтение кода при сомнении |

**Провал любого пункта — этап B не считается выполненным**, задание в
целом ниже проходного балла независимо от этапов C–D.

## Этап C — 25 баллов (обязателен для оценки выше удовлетворительной)

| Критерий | Баллы | Как проверить |
|---|---|---|
| Проверка имени хоста реализована отдельно от штатной проверки цепочки/срока платформы | 5 | Чтение кода: штатная проверка «по умолчанию» как единственный механизм — 0 за весь этап |
| Порт с чужим CA → `tls_error`, `FACT` называет причину, доступную из ошибки платформы (например «неизвестный издатель») | 5 | Прогон по всем 4 портам, сверка класса и текста `FACT` |
| Порт с истёкшим сертификатом → `tls_error`, `FACT` цитирует именно истечение срока (не тот же текст, что для чужого CA) | 5 | — |
| Порт с несовпадающим именем → `cert_invalid` (не `tls_error`!), `FACT` называет и запрошенное, и полученное имя | 5 | — |
| Валидный порт → `http_ok`, HTTP-обмен поверх TLS работает (переиспользован код этапа A/B) | 5 | — |

Частые ошибки: (а) оба `tls_error`-порта дают одинаковый обобщённый
`FACT` вроде «TLS handshake failed» — значит, конкретная причина отказа
платформы не читается, исключение просто ловится целиком; 0 за
соответствующий критерий, даже если `CLASS` формально верный;
(б) несовпадение имени тоже вылетает как `tls_error` — значит,
автоматическая проверка имени не была отключена и своя проверка не
написана; 0 за этот критерий целиком, поскольку задание проверяет именно
самостоятельную реализацию этой конкретной проверки.

Этап C выполнен только при выполнении всех пяти критериев (25 из 25).

## Уровень 2 — этап C, углублённый — 35 баллов (бонус, не входит в базовые 100; не обязателен для зачёта)

Проверяется только если сдан режим уровня 2. Отсутствие этого режима —
уровень 2 не оценивается, это нормально: зачёт уже дан этапами A–C
уровня 1.

| Критерий | Баллы | Как проверить |
|---|---|---|
| Режим уровня 2 реально не использует штатную автоматическую проверку цепочки — вся проверка (подпись/издатель/срок) собственным кодом | 5 | Чтение кода — это условие входа в раздел, при делегировании платформе остальные пункты не проверяются |
| Чужой CA → `chain_untrusted` (не смешан с `cert_expired`) | 5 | Прогон по 4 портам без доп. флагов |
| Истёкший → `cert_expired` (отдельно от `chain_untrusted`) | 5 | — |
| Несовпадение имени → `hostname_mismatch` | 5 | — |
| Валидный → `http_ok` | 3 | — |
| Обход истёкшего срока на истёкшем порту → обмен продолжается, `BYPASSED: expired` присутствует и называет срок | 4 | Явный флаг/параметр обхода, указанный в README сдачи |
| Обход несовпадения имени аналогично на порту с неверным именем | 4 | — |
| Pinning по отпечатку сертификата принимает порт с чужим CA при верном отпечатке | 2 | Отпечаток проверяющий считает независимо (штатной утилитой платформы) |
| Pinning с заведомо неверным отпечатком **не** обходит проверку (остаётся `chain_untrusted`) | 2 | Критично: подставить случайный отпечаток — если тоже пропускает, это не pinning, а скрытое отключение проверки, весь пункт — 0 |
| В клиенте нет общего флага-аналога «insecure», отключающего все проверки разом | 0 (условие) | Чтение кода: наличие такого флага обнуляет весь раздел «Уровень 2» целиком, независимо от остальных пунктов |

| Критерий | Баллы |
|---|---|

| Абзац про «чужой CA»/«истёк» как один `tls_error` (различимы только по тексту причины из ошибки платформы) против имени как отдельной ручной проверки — со ссылкой на конкретные порты стенда, не пересказ теории | 5 |
| Абзац про `parse_error` vs `framing_error` — точно называет, что уже гарантировано к моменту отказа | 5 |

Отчёт, который верно пересказывает лекцию, но не привязан к собственным
прогонам (нет конкретных портов/кейсов/фактов), — не более 5 из 15.

## Итоговая шкала (базовая часть без бонуса, 100 = A+B+C+REPORT)

Отчёт обязателен для зачёта. Без этапа C пункт отчёта о собственных
TLS-прогонах получает 0 из 5; остальные пункты оцениваются обычным образом.
Провал любого критерия A или B означает незачёт независимо от суммы баллов.

| Диапазон | Значение |
|---|---|
| < 60 либо провален A/B либо отсутствует отчёт | не зачтено, пересдача |
| 60–74 | зачтено, минимальный уровень |
| 75–89 | зачтено, хороший уровень |
| 90–100 | зачтено, отличный уровень |
| + бонус этапа D (10) | добавляется к итогу сверх 100, не подменяет базовые баллы |
| + бонус уровня 2 (35) | добавляется к итогу сверх 100 независимо от этапа D; можно сдать один бонус, оба или ни одного |

Без выполненного этапа C итог базовой части ограничивается 74 баллами,
независимо от суммы за этапы A, B и `REPORT.md`.
Уровень оценки определяется базовой частью с этими ограничениями.
Бонусные баллы учитываются отдельно: они не превращают незачёт в зачёт,
не снимают потолок без C и не повышают уровень оценки по таблице.

## Типичные способы «обойти» задание и как они ловятся

- Обёртка над готовым HTTP-клиентом с косметическим низкоуровневым кодом
  сверху — видно по коду и по факту отсутствия ручного framing (chunked
  и broken-length почти всегда либо работают «слишком хорошо», либо не
  работают вовсе).
- Один общий перехват всех исключений на всё — не различает классы,
  проваливает большинство точечных проверок этапов A–C по таблицам выше.
- Копирование текста объяснения из лекции в `REPORT` без привязки к
  своим прогонам — ловится требованием конкретных портов/кейсов в отчёте.
- Уровень 2: обход по отпечатку/названному дефекту, который на самом деле
  не сравнивает аргумент ни с чем и работает как скрытое глобальное
  отключение проверки — ловится обязательным тестом с заведомо неверным
  отпечатком (см. таблицу уровня 2). Это самая частая имитация: код
  выглядит как «настоящий pinning», но флаг фактически ничего не
  проверяет.
